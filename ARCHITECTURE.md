# Architecture

PestLaunch **Call Intelligence**: upload a call recording, get a transcript,
call type, outcome, scorecard grade and coaching. The UI and the backend API
live in this one Next.js app.

The code is feature-sliced. Each feature is a **module** that can be turned on
or off per tenant (pest control company).

```

instrumentation-client.ts  Runs in the browser before the app is interactive: guards view transitions
app/                     Routing only: thin pages, layouts, route handlers
  page.tsx               Landing page (signed-in users go straight to their workspace)
  _landing/              Landing sections, the 3D hero scene and its invented demo call
  (auth)/                /login, /signup, /onboarding
  [tenant]/              UI, e.g. /noble-pest/calls
    _components/         TenantNav (enabled modules, Settings, user menu), PageSkeleton
    _lib/                requireModule (auth + membership + module check)
```

Every module has the same shape:

```
modules/<name>/
  module.ts    Manifest: id, defaultEnabled, dependsOn, nav
  index.ts     Public UI API: manifest, components, types
  server.ts    Public server API: services, route handlers, analysis steps
  ui/          Components
  server/      Server-only code (starts with import "server-only")
  model/       Types and pure domain logic
  config/      Static data, e.g. the scorecards
  lib/         Module-private helpers
  server/schema.ts  The module's own database tables (optional)
```

## Dependency rules (enforced by ESLint)

`app → modules → core → shared`. A layer imports only from layers to its right.

- A module never imports another module. Share code through `core/` or
  `shared/`; compose modules in `app/` or the registries.
- `app/` imports a module only through `@/modules/<name>` or
  `@/modules/<name>/server`.
- Service functions take the tenant explicitly so every query is tenant-scoped.

## Data and auth

- **Postgres** on Supabase (production) or the Supabase CLI's Docker stack
  (local). Platform tables live in `core/db/schema.ts`; a module's own tables
  live in its `server/schema.ts` (e.g. `calls` in the calls module).
  drizzle-kit reads both and generates migrations into `drizzle/`.
- **Calls** are one row each in `calls`: status, file name, recording path,
  call type, employee, and JSON columns for the transcript, outcome and
  per-module `analyses`. Rows belong to a tenant and are always queried by it.
- **Auth** is Supabase Auth with email and password, using cookies through
  `@supabase/ssr`. `proxy.ts` refreshes the session on every request.
- **Tenancy:** `tenants`, `tenant_members` (with a `role_id` and a
  `display_name`), `tenant_roles`, `tenant_invites` and `tenant_modules`
  (per-tenant module overrides). Sign-up creates the user, a tenant with the
  default roles, and an owner membership.
- **Permissions, not roles:** the app only ever checks permissions
  (`can(access, "calls.delete")`), listed in `core/tenancy/permissions.ts`:
  `calls.upload`, `calls.view_all`, `calls.assign`, `calls.delete`,
  `coaching.manage`, `team.manage`, `roles.manage`, `company.manage`, `modules.manage`, `calltypes.manage`. A role is
  a per-tenant row holding a list of them, so a tenant can add custom roles
  in Settings without code changes. Every tenant starts with Owner (every
  permission, locked), Manager (calls and team) and Rep (upload only).
  Guards: nobody can grant a role, or build one, with permissions they don't
  have; only an owner can make someone an owner; a tenant can't lose its last
  owner.
- **Invites:** a link with a random token (`/invite/[token]`, valid 14 days).
  The invitee signs up (the email is locked to the invited address, and no
  company is created) or logs in, and joins with the invite's role. Only the
  invited email can accept it. No email server is needed: the inviter copies
  the link.
- **Calls belong to members.** `calls.employee_id` is the team member; the
  name heard in the call (`employee_name`) is only a hint. A member without
  `calls.assign` uploads calls as their own, whatever the recording says.
  Someone with it picks the member, or leaves "Work it out from the call",
  and processing assigns the one member whose first name matches the heard
  name. Calls can be reassigned on the call page, which flags a mismatch with
  the heard name. Without `calls.view_all` a member only sees their own calls
  and coaching, enforced in the queries (`callScope`), so other calls 404.
- **Authorization** is enforced in the app, not by RLS. Every table has RLS
  enabled with no policies, so Supabase's public REST API returns nothing.
  The server reads data over a direct Postgres connection and checks access
  with `requireTenantAccess` (pages) and `checkTenantAccess` (APIs). A tenant
  the user isn't a member of returns 404, the same as one that doesn't exist.
- **Recordings** go to the private `recordings` storage bucket, under a
  folder per tenant (`<tenantId>/<uuid>.<ext>`). It has no policies, so only
  the server (secret key) can read it. The API rejects a path outside the
  caller's tenant folder.
- Auth checks call `connection()` so they always run per request and never
  end up in a prerendered or prefetched shell.

## Call processing

Recordings never pass through our API, because they're often bigger than
the 4.5 MB request limit on serverless hosts:

1. `POST /api/[tenant]/calls/uploads` with `{ fileName, size }` checks the
   type and size (50 MB max) and returns a storage path in the tenant's
   folder plus a one-time upload token.
2. The browser uploads the file straight to storage with that token
   (`core/storage/client.ts`).
3. `POST /api/[tenant]/calls` with `{ path, fileName }` checks the file is
   there, creates the `calls` row (status `processing`) and answers 202 right
   away. `modules/calls/server/process-call.ts` runs after the response with
   Next's `after()`; the route sets `maxDuration = 300` so the platform lets
   it finish.

While a call processes, `stage` records the step (transcribing, analyzing,
reviewing). The call list refreshes every 5 seconds while any call is
processing, and the call page every 4 seconds with a step-by-step progress
card.

`after()` isn't a durable queue: if the server stops mid-way (a deploy, a
crash, a platform time limit), the row would stay `processing`. A call that
hasn't moved on for 10 minutes is shown as failed. `POST
/api/[tenant]/calls/[callId]/retry` (the Retry button) runs a failed call
again, reusing its transcript when it has one. The retry claims the row
with one conditional update, so two clicks can't start it twice.

Answers are also checked for completeness: grading must cover every
scorecard item, and speaker labelling every line, or the request is retried.
Without this, a model that stops early would make skipped items count as
missed. AI rate limits are retried using Retry-After. A wait longer than a minute
(e.g. a daily token limit) moves the request to the fallback chat
model (`AI_CHAT_FALLBACK_MODEL`, default `gpt-5.4-mini`), and the server
remembers the main model is limited until it resets, so later requests go
straight to the fallback. If the fallback is limited too, the call fails at
once with a message saying when to retry. The speaker-label schema is kept
flat (a number and a speaker per line, splits listed separately) because the
smaller model follows flat shapes more reliably.

The pipeline downloads the recording and saves each stage as it finishes, so
a failure keeps whatever already worked and sets status `failed` with the
error:

1. **Transcribe** (`transcribe.ts`) with speaker labels:
   - Whisper (`whisper-1` on OpenAI) returns timed segments. A vocabulary
     hint helps it spell the trade's words, and starts with the company's
     name and its team members' names, so names aren't guessed from the
     sound (`whisperPrompt`).
   - A segment is dropped as silence only when Whisper thinks it's probably
     not speech *and* the text is a low-confidence guess (no-speech > 0.6
     and average log-probability < -1, Whisper's own rule). The no-speech
     score alone isn't enough: whisper-1 shares it across a 30-second
     window, and a stricter cutoff silently lost up to a minute of real
     speech on 9 of the 20 test calls. Whisper can also get stuck repeating
     a sentence; segments with a compression ratio over 2.4 (its own loop
     check) are dropped, and so is a line of 5+ words that repeats one of
     the 4 lines before it (`dropRepeats`). A recording with fewer than 5
     words is rejected: on silence Whisper invents text such as "Thank you."
   - **Card details are masked** before the transcript is stored or sent to
     a language model (`redactPaymentDetails` in `lib/transcript.ts`, unit
     tested). Customers read card numbers out four digits at a time over
     several lines, often minutes after the card was first mentioned. Digits
     become `[redacted]` within a minute either side of a line mentioning a
     card, its expiry, code or brand; in a read-back (neighbouring lines,
     within 20 seconds, that are little more than digit groups); and in any
     13–19 digit run. Prices, percentages, dates, times and phone numbers
     are kept, and the cue words are specific ("credit card", not "credit").
   - Whisper doesn't say who is talking, so the chat model (`gpt-5.5`) labels each
     segment employee, customer or unknown (phone menus, hold messages). It
     works in chunks of 40 lines, each shown the call's opening lines and the
     lines just before it. When one segment holds two speakers, the model can
     split it; the split is kept only if its pieces are exactly the segment's
     words, so no text is invented.
   - Consecutive lines from the same speaker are joined into turns of up to
     about 30 seconds.
2. **Analyze** (`analyze-call.ts`): one chat-model request with a strict
   schema returns the call type, the employee's name, a short summary, the
   resolution (booked, retained, cancelled, resolved, follow-up needed,
   unresolved), key details and open follow-ups. The call type definitions
   come from the call manuals and judge the caller's real purpose, not the
   phone menu option. The prompt asks for facts said in the call only, with
   dates as spoken and no invented follow-ups. Retention calls also get a
   `cancelReason` from a fixed list (Price, No longer needed, Service
   quality, Moving, Switching company, Scheduling, Other) so reasons can be
   counted. A quote that didn't book is never "resolved" (follow-up needed
   or unresolved). Follow-ups include every promise, even on booked calls
   (notes for the technician, payment at the visit, a callback). Summaries
   say "the company" rather than its name, which the audio often garbles.
3. **Module steps**: run the `CallAnalysisStep` of every enabled module
   (scorecards, coaching, sentiment) in parallel. Each result is stored under
   `analyses[moduleId]`.
   - Sentiment: see "Sentiment" below.
   - Scoring: see "Call types and scorecards" below.
   - Coaching (`modules/coaching/server/coaching-step.ts`): grounded in the
     manuals' four-step call process plus notes for sales, retention and
     re-service calls. Returns up to 3 strengths (only things the employee
     actually did), up to 3 improvements, each with a quote and a line the
     employee could say next time, and one focus for the next call. Quotes are
     kept only if they appear in the transcript. Suggestions never use
     placeholder or invented prices. A call where the employee never speaks
     (a voicemail) gets no coaching.

The calls module never imports scorecards or coaching. The route asks
`registry.server.ts` for the enabled steps and passes them in. Turning a module
off for a tenant removes both its UI and its processing step.

## Rep page

`/[tenant]/team/[repId]` (linked from each team member's card on Team):
average score, trend (needs 4 scored calls), close rate and cancels saved;
**What to work on**, the steps the rep misses most with the manual's
criteria for each (`stepCriteria`), as "what good sounds like"; a score-by-call
chart linking to each call; the latest coaching focus with a "Try saying"
line; their plays and follow-up tasks; and recent calls. A rep can open their
own page; other reps' pages need `calls.view_all`.

## Review and corrections

AI results can be wrong, so people with `calls.review` (Owner and Manager by
default) can check and correct them on the call page:

- **Review card:** change the call type or outcome, add a note, or just mark
  the call reviewed. A new call type re-scores the call in the background
  against the right scorecard (`rescoreCall` reruns only the module steps, so
  the correction isn't undone).
- **Scorecard steps:** each pass or fail mark becomes a button. Flipping one
  recomputes points and grade (`overrideScorecardItem`, unit tested) and tags
  the step "Corrected by <name>".
- `calls.review` stores who, when, the note, and every change in words
  ("Outcome: Booked → Resolved"), shown on the call. The header and the Call
  Log show **Reviewed**.
- **Needs review:** unreviewed calls are flagged when no rep was identified,
  the speaker labels look lopsided or unattributed (`callReviewFlags`), or
  the grade is one point either side of a boundary (`scorecardReviewFlag`).
  The Call Log has a Needs review filter; the call page lists the reasons.
  The list has no transcripts, so speaker checks only run on the call page.

## Search and export

- **Quick search** (⌘K, Ctrl K or "/" anywhere, or Search in the sidebar):
  one box for pages, calls and reps. Before you type it lists the main
  pages and the latest calls. `searchWorkspace` (a server action in
  `app/[tenant]/_lib/search-actions.ts`) asks the calls module's
  `searchCalls`, which ranks calls by their details (title, rep,
  customer, pest, type, outcome; `modules/calls/lib/search.ts`, unit tested)
  and adds calls that only match in the transcript, with the line. Results
  only include what the viewer could open: their own calls without
  `calls.view_all`, and reps only for people who can see others' pages.
  Arrow keys move, Enter opens, Esc closes, and late answers to older
  queries are dropped.
- **Transcript search** (`?q=` on `/[tenant]/calls`): finds calls where any
  transcript line contains the words (case-insensitive, in Postgres over the
  JSON transcript), and shows the matching line, who said it and when.
  Scoped like the call list.
- **CSV export** (`GET /api/[tenant]/calls/export`, the Export CSV button):
  every call the member can see, with type, rep, outcome, cancel reason,
  score, talk time, summary and follow-ups. Cells are quoted, and text a
  spreadsheet would run as a formula is defused (`modules/calls/lib/csv.ts`,
  unit tested).

## No separate leads

There's no Leads page. PestLaunch OS is the CRM, so Call Intelligence feeds
it rather than keeping a second pipeline: an unbooked sales call is a **Sale
not closed** leak (Overview, and Needs an owner on Follow-ups) that shows who
called, what for and the price given, how long it's been waiting and the next
step, and assigning it makes a follow-up with an owner. Close rate comes from
the calls themselves. A `leads` table existed earlier and was dropped
(`drizzle/0012_drop_leads.sql`).

## Overview dashboard

`/[tenant]` answers an owner's questions at a glance, for 7 days, 30 days or
all time (`?range=`). The maths is a pure function in
`app/[tenant]/_lib/insights.ts`; the page builds its input from the calls and
scorecards modules. Call types are grouped the way PestLaunch's Call Log does
(`CALL_TYPE_GROUP`: Sales, Service, Billing, Retention, Other).

- **Scorecard:** calls and talk time; close rate (sales calls booked); cancels
  saved (retention calls retained); follow-ups open; average score with the
  grade split.
- **Leaks:** calls that lost money or still need someone to act, newest first:
  sales not closed, customers who cancelled (with the reason), follow-ups
  owed, and calls graded Below Standard.
- **Assignable leaks:** anyone with `calls.assign` picks a teammate from a
  leak's Assign control, which creates a follow-up task on that call
  (`call_tasks`, owned by the calls module). The leak then shows its owner.
  The Follow-up tasks card lists the team's tasks for assigners, with a
  Mine / Team switch that opens on Mine when they have open tasks, and "Your
  tasks" for everyone else; the assignee or an assigner marks them done.
  The Overview card shows the first 5 with a link to Follow-ups.

## Follow-ups

`/[tenant]/follow-ups` (a nav item from the calls module) is the to-do list
for calls: everything someone has been asked to follow up on. Mine / Team
(Team only with `calls.assign`) and Open / Done live in the URL
(`?view=&status=`), so links can open "my open follow-ups"; assigners land
on Mine when they have something open. Each task shows its call, owner and
how long it's been waiting, with a circle to mark it done. For assigners,
**Needs an owner** lists the leaks (same rules as the Overview) that have no
open follow-up yet, each with Assign. The leak row and the Overview's call
list builder are shared (`LeakRow`, `_lib/dashboard-calls.ts`).

Your open follow-ups are counted as a badge on Follow-ups in the sidebar and
the mobile bar, a call's page shows its follow-ups and whose they are at the
top, and quick search has "My follow-ups".
- **Reps:** calls, close rate and average score per rep (hidden for members
  without `calls.view_all`, who see only their own numbers).
- **Why customers cancel:** each reason with saved vs lost.
- **Get set up:** a first-run checklist above everything else: upload a
  call, invite the team, check a call's score, assign a follow-up. Each step
  is ticked off by what's in the workspace (a call exists, someone else was
  invited, a call was reviewed, a task exists), never by a click, and steps
  the viewer can't do are left out (`app/[tenant]/_lib/setup.ts`, unit
  tested). It shows only with two or more steps, so reps never see it, and
  disappears when everything is done. The × hides it for that browser (a
  cookie per company).

## Navigation and wording

The sidebar is Overview · Calls · Follow-ups · Team, then Settings. The company's
name sits at the top with "Powered by PestLaunch", as in PestLaunch OS, with
the Search box (quick search, ⌘K) under it. The
scorecard rubric isn't in the sidebar; each call's score links to it
("How calls are graded"), set with `inSidebar: false` on the module's nav
item. Words follow PestLaunch OS: Rep and Caller (not Employee and Customer),
Outcome, Talk, and Successful for calls that were booked, saved or resolved.

## UI and design

The look follows the Freehold design system: the Outfit font, rounded cards
and mint accent pills, in dark and light.

- **Theme:** System, Light or Dark, picked on the Settings page and saved in
  the `pestlaunch-theme` cookie (no server round trip). A boot script in
  `shared/config/theme.ts` reads the cookie and sets `<html data-theme>` before
  first paint, so there's no flash. System follows the device, and dark is
  the default when the device can't be read. `ThemeSync` (root layout) keeps
  System in step when the device switches while the page is open.

- Colour tokens are CSS variables in `app/globals.css`, exposed to Tailwind
  as `bg-card`, `text-muted`, `text-accent`, etc. Use tokens, not raw colours,
  so both themes work. Every fill has an `on-` partner for text on top of it.
- Shared building blocks are in `shared/ui/`. Each page uses `PageStack` and
  `PageHeader` so pages line up the same way.
- Module nav items carry an icon (`nav[].icon` in `module.ts`), shown in the
  sidebar and the mobile bottom bar.

## Motion

Navigation moves the way Freehold does, built on React's `<ViewTransition>`
(no animation library; Next.js runs every navigation as a transition). Each
animation says one thing:

| What you see | Means | Where |
| --- | --- | --- |
| The old page fades out fast; the new one fades in and rises 8px | You went somewhere else | `PageStack` (every page's root) and `SettingsPage` |
| A loading skeleton fades out as the real content fades in | The data arrived | `PageExit` around `PageSkeleton` and `SettingsBodySkeleton` |
| The accent pill glides to the item you picked | Where you are now | `NavPill` (`shared/ui/nav-pill.tsx`) in the sidebar, mobile bar and settings menu |

- The page stays live: the root snapshot isn't animated, so the sidebar never
  freezes and clicks pass through. Only these named pieces animate.
- Menu labels have their own transition names (`navLabelStyle`), so they draw
  above the moving pill and their colour cross-fades.
- Transform and opacity only, 140 to 380ms, one ease-out curve. All of it is
  in `app/globals.css` (search for "Navigation motion") and is turned off
  under `prefers-reduced-motion`.
- Browsers without view transitions (older Safari and Firefox) simply don't
  animate; nothing else changes.
- **Aborted transitions are expected, not errors.** The browser aborts a
  transition when the window is resized mid-way, the tab is in the background,
  or a newer navigation interrupts it. React chains `finished.finally()` and
  never handles the rejection, so every abort showed as an "Uncaught (in
  promise) InvalidStateError/TimeoutError". `guardViewTransitions`
  (`shared/lib/view-transitions.ts`, installed by `instrumentation-client.ts`)
  makes `finished` and `updateCallbackDone` settle quietly, and skips any
  transition still running after 1 second, since React holds the next
  navigation until the current transition ends. As a second layer,
  `ignoreAbortedViewTransitions` drops any aborted transition that still ends
  up unhandled (one started outside React, or on a page loaded before the
  guard). It listens in the capture phase so Next's dev overlay never counts
  it, and only matches the browser's own "Transition was aborted/skipped"
  errors; every other rejection passes through.
- Navigations are lateral (sidebar items are siblings), so there are no
  directional slides. Revalidations and form saves don't animate: every
  `<ViewTransition>` uses `default="none"`.

## Calls UI

| Page | What it does |
| --- | --- |
| Call library | Drag-and-drop upload of one or several recordings, each checked in the browser (type, 50 MB) before anything is sent; a queue uploads them one at a time ("2 of 5") and each then processes in the background. Progress shows the upload and processing steps with a timer, warns before leaving the page, and refreshes the list so the new call shows as processing. Four headline numbers (calls, win rate, open follow-ups, talk time). Filters like PestLaunch's Call Log: outcome (won, follow-up, lost, processing, failed), type group (Sales, Service, Billing, Retention, Other), rep and date, plus search by name, type, rep or summary, all in the browser. Columns use PestLaunch's words: Rep, Score, Outcome, talk time. Managers see a "Whose call?" picker on upload. |
| Call detail | The scorecard leads (the `lead` slot, sections in two columns when the panel is wide, via a container query), then the outcome, coaching and the review card. The recording and transcript are reference: a sticky right column on wide screens that scrolls on its own, and a fixed-height box at the end on smaller ones, so a long call never pushes the score down. The player sits on a speaker timeline (who talked when, and each side's share of talk time) above the transcript. Clicking a line's time plays from there, the playing line is highlighted, and the transcript can be searched. Owners and managers can delete a call from here. A processing call refreshes itself. |

The calls module never imports scorecards. The list's score column comes in
through `CallsPage`'s `score` prop, which the app page fills with its own
`ScoreBadge` (`app/[tenant]/calls/_components/`), built on the scorecards
module's public `getScorecardResult`. The recording plays from a
short-lived signed URL (`getCallRecordingUrl`), so the bucket stays private.

## Call types and scorecards

Every company starts with these call types and scorecards, from the call
manuals in `../docs/call-manuals/` (the two office manuals are the same
manual for two companies, with identical scorecards):

| Call type | Scorecard | Max | Gold | Green |
| --- | --- | --- | --- | --- |
| New customer (sales) | Sales Calls | 17 | 17 | 14+ |
| Retention | Retention Calls | 12 | 12 | 11 |
| Scheduling, billing, re-service | All Calls | 12 | 12 | 11 |
| Other | Not scored | | | |

Sections follow the manuals' four steps (Validate, Understand, Solve,
Verify), plus Pricing and Objections on sales calls. On sales calls with no
objections, the 4 objection points are awarded automatically. A clash over
appointment times or a question about paying isn't an objection.

The defaults are data in `core/calls/defaults.ts` and
`core/calls/default-scorecards.ts`. Each item carries its criteria,
paraphrased from the manual's definition of that step; the grader and the
Scorecards page both show them, so managers and the AI judge by the same
rule.

### Per-company call types

Call types are configurable per company (`core/calls/catalog.ts`, unit
tested). A company's catalog is the defaults with its changes laid over them,
then the types it created ("custom-…" keys). Built-ins only get a row in
`tenant_call_types` once edited, so "Reset to default" just deletes the row;
own types always have one. Each type has a name, a description (how to
recognise it; the AI classifies calls by these), a dashboard group (Sales,
Service, Billing, Retention, Other, so the Overview, Follow-ups and filters work
for any type), an optional scorecard, and an on/off switch. "Other" is
always on, as the catch-all.

- **Classifying:** `analyzeCall` gets the company's enabled types and builds
  the call-type enum and guide from them. An unbooked sales-group call is a
  Sale not closed leak.
- **Grading:** the scoring step uses the call's type definition's
  scorecard. Results save the scorecard's name, Gold/Green lines and each
  step's criteria, so an old call still reads right after its company edits
  or deletes the scorecard. An edited scorecard is keyed by its call type,
  so it never mixes with a shared default.
- **Detection mode** (`tenants.call_type_mode`): Automatic (the AI picks) or
  Ask on upload (the upload form gets a Call type picker, "Let the AI
  decide" by default). A picked type, or one a reviewer corrects, sets
  `calls.type_locked`, and the AI never changes it, even on a retry.
- **Pages read names from the catalog:** calls are read with their
  `callTypeName` and `callTypeGroup` resolved, so every page shows a
  company's own names. A deleted type on an old call reads "Removed type".
- **Settings → Call types** (needs `calltypes.manage`; owners have it):
  the detection switch, the list with on/off switches and call counts, and
  an editor (name, description, group, scorecard sections and steps,
  Gold/Green). Own types can be deleted only if no call uses them.
- **Create with AI:** describe the calls or paste part of a manual, and one
  structured-output request drafts the name, description, group and a
  scorecard in the company's four-step style. It only fills the editor;
  nothing is saved until the person reviews it.

Grading (`modules/scorecards/server/scoring-step.ts`): one structured-output
request gets pass/fail, an evidence quote and a one-line reason per item,
plus whether the customer raised objections. A quote is kept only if its
words really appear in the transcript, so every quote shown can be trusted.
Points and grade are computed in code from the scorecard, never by the
model. One line earns one step: the model kept double counting despite the
prompt, so `scoreCall` enforces it. When two passing steps quote the same
line, the later step in scorecard order keeps it (a reused line is nearly
always the call moving forward, e.g. a confirm line is the Close, not the
earlier Confidence) and the earlier one fails with the reason, except for
natural pairs (Consensus and Close, Present Solution and Close,
Close and Provide a Conclusion). Short scheduling and billing calls are
graded on the manual's lighter version of the steps, but a greeting is
never Investigate and offering a slot is never a Summary.

## Module toggling

1. Each `module.ts` declares `defaultEnabled` and optional `dependsOn`.
2. A tenant stores overrides in `tenant.modules`, e.g. `{ coaching: false }`.
3. `resolveEnabledModules` applies the overrides, then turns off any module
   whose dependencies are off.
4. Every module page calls `requireModule(params, "<id>")`, and API routes use
   `withModule("<id>", handler)`. Server actions must check `isModuleEnabled`.
   Don't rely on a layout for this: Next renders layouts and pages in
   parallel, so a layout check alone still lets a disabled page render and
   send its data.
5. After changing a tenant's modules or name, expire its cache tag:
   `updateTag(tenantCacheTag(slug))` in a server action (the user sees the
   change at once), `revalidateTag` elsewhere.

Owners switch modules on the Settings page (`app/[tenant]/settings`). It
writes `tenant_modules` rows. The base module (`baseModuleId` in
`registry.ts`, Calls) can't be turned off, and a module can't be turned on
while a module it depends on is off.

## Settings

`/[tenant]/settings`, linked at the bottom of the sidebar and in the mobile
bar. Like Freehold's settings, each section is a card with its title and
explanation on the left and the controls on the right (stacked below `xl`).
Settings is split into pages so it never becomes one long scroll.
`layout.tsx` renders the header and a settings menu (a column beside the page
on wide screens, a row above it on small ones), so moving between pages only
reloads the content. Every change is a server action with zod validation and
a server-side permission check.

| Page | Section | Who can change it | Saved in |
| --- | --- | --- | --- |
| Profile (`/settings`) | Display name | Everyone, for themselves | Supabase Auth user metadata (`full_name`); the session is refreshed so the new name shows at once |
| Appearance | Theme: preview cards for System, Light, Dark | Everyone | `pestlaunch-theme` cookie (browser only) |
| Company | Company name | `company.manage` | `tenants.name`; the URL slug never changes |
| Company | Modules | `modules.manage` | `tenant_modules` |
| Call types | Detection mode, call types and scorecards | `calltypes.manage` | `tenants.call_type_mode`, `tenant_call_types` |
| Members | Members, invites, member roles, remove | `team.manage`; everyone sees the member list | `tenant_members`, `tenant_invites` |
| Roles | Custom roles and permissions | `roles.manage`; everyone sees the roles | `tenant_roles` |

Without the permission a section shows read-only.

## Adding a module

1. Create `modules/<name>/` with the shape above and register it in `registry.ts`.
2. If it analyzes calls, export a `CallAnalysisStep` from its `server.ts` and
   add it in `registry.server.ts`.
3. Add `app/[tenant]/<name>/page.tsx` (calls `requireModule` first) and a
   `loading.tsx` next to it (re-export `PageSkeleton`). Each page needs its
   own boundary so client navigations between modules stay instant.
4. For APIs, add `app/api/[tenant]/<name>/route.ts` using `withModule`.

## Testing

Unit tests use Vitest and sit next to the code they test (`*.test.ts`). They
cover pure logic only, with invented data: no network, database or env vars,
so they run in well under a second and the same way in CI.

| What | Tested in |
| --- | --- |
| Points, grades and which scorecard grades a call type | `modules/scorecards/model/grade.test.ts` |
| Scoring a call: auto-awarded objections, quotes kept only when they're the employee's words | `modules/scorecards/model/score-call.test.ts` |
| Permission checks and who may grant which role | `core/tenancy/rules.test.ts` |
| Transcript rules: dropping non-speech, accepting speaker splits, joining turns | `modules/calls/lib/transcript.test.ts` |
| The Coaching page's per-person summaries (grouping, trend, most-missed items) | `modules/coaching/model/team.test.ts` |

To keep logic testable, it lives in pure files and the server code calls it:
`scoreCall` (model/score-call.ts) is what `scoring-step.ts` runs on the
model's judgements, the transcript rules are in `modules/calls/lib/transcript.ts`,
and `can`/`canGrantRole` are in `core/tenancy/rules.ts`. Anything that talks
to the AI, Postgres or storage isn't unit tested; it's covered by running
real (invented) calls through the app.

`vitest.config.mts` maps the `@/` alias and swaps `server-only` (which throws
outside a Next server build) for an empty stub.

## AI models

Each AI job uses the cheapest model that matched the best one in testing. Jobs ask
`generateObject` for a tier; the tier's model comes from the environment
(`core/ai/models.ts`, unit tested).

| Job | Tier | Default model | Why |
| --- | --- | --- | --- |
| Scoring | best | `gpt-5.5` (`AI_CHAT_MODEL`) | The core result. The smaller model differed on 9% of scorecard steps. |
| Call type and outcome | best | `gpt-5.5` | Outcomes drive Leaks and follow-ups. The smaller model called a "wants to think" quote unresolved instead of follow-up needed. |
| Speaker labels | best | `gpt-5.5` | They feed every later step. Re-labelling 3 real calls' saved text, `gpt-5.5` matched its stored labels on 100% of words and `gpt-5.4-mini` on 99.2% (97.9% on the longest), on text easier than raw Whisper output. |
| Coaching | fast | `gpt-5.4-mini` (`AI_CHAT_FAST_MODEL`) | Feedback as specific as `gpt-5.5`'s (quotes from the call, lines to say), usually two improvements instead of three, at about a third of the cost. |
| Sentiment | fast | `gpt-5.4-mini` | Agreed with `gpt-5.5` on 94% of lines and never read a line as the opposite tone. |
| Call type drafts (Settings) | best | `gpt-5.5` | Rare, so cost doesn't matter. |

How it was decided: four invented demo calls were voiced with two different
text-to-speech voices (so every line's speaker is known) and run through the
real pipeline on `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini` and `gpt-5.4-nano`.
`gpt-5.4` saved little (it writes more, so its coaching cost more than
`gpt-5.5`'s), and `gpt-5.4-nano` agreed on only 74% of sentiment lines. `gpt-5.5`
itself varies by about a point between runs on the same call, so differences
of a point are noise. Speaker labels looked equal on that clean audio, so they
were also checked on 3 real calls (text only, no re-transcribing), where the
smaller model fell short; they stay on `gpt-5.5`.

Measured cost per short demo call: about $0.079, down from $0.085 with
`gpt-5.5` for everything; coaching costs about a third and sentiment about a
third of before. Prices used: `gpt-5.5` $5 / $30 and `gpt-5.4-mini` $0.75 / $4.50 per
million input / output tokens. The fast tier falls back to `AI_CHAT_MODEL`
when its model is unavailable or limited, so it never fails a call; a provider
without `gpt-5.4-mini` (e.g. Groq) also falls back, or set
`AI_CHAT_FAST_MODEL` (see `.env.example`).

The account's measured rate limits are 5,000 requests a minute on both models
(1M tokens a minute on `gpt-5.5`, 2M on `gpt-5.4-mini`), with no daily cap.

## Sentiment

`modules/sentiment` shows how the customer felt through a call and where it
turned. It's a module, so a company can turn it off in Settings, and the call
page looks exactly the same without it.

- **What the AI does:** one low-effort request per call labels every
  transcript turn positive, neutral or negative with a strength from 1 to 3.
  To keep cost down the answer is one short code per line ("12x3" is line 12,
  negative, strong); a line it skips or garbles counts as neutral rather than
  paying for a retry. Calls under 4 turns (voicemail, wrong number) are skipped.
- **What's computed in code** (`model/sentiment.ts`, unit tested): only the
  labels are stored, so improving this applies to calls already analysed.
  - The recording split into positive, neutral and negative ranges.
  - The customer's mood over time, smoothed so one line doesn't swing it.
  - Where it turned: became upset, calmed down, turned positive, each with
    the customer's own words.
  - How the customer started compared with how they ended, and the share of
    talk time per sentiment.
- **On the call page:** the ranges draw as a lane under the player's speaker
  timeline, through CallDetail's generic `timelineBands` prop, so the calls
  module never imports sentiment. A compact panel after coaching leads with
  the story: how the customer started and ended (Upset, Neutral, Happy) and a
  coloured trend chip (Improved, Got worse, Steady). Then the mood curve,
  filled green above the middle and red below with the neutral band shaded,
  its labels in a gutter so they never cover the line, and clickable markers
  where it turned (hover anywhere for the customer's words); a stacked bar
  of talk time per sentiment; and the turning points, each with a time button
  that jumps the player (`#t=` links). Any `#t=SECONDS` link on the call page moves the player and scrolls
  the transcript there, also on load, also for demo calls without audio.
- **Colours** are a diverging pair (`--mood-positive`, `--mood-negative`, a
  gray `--mood-neutral`), validated for colour blindness against the card in
  both themes. Dark mode uses its own steps. Labels and position always carry
  the meaning too.
- **Limits:** it reads the words, not the tone of voice. Sarcasm or a
  flat "fine" can read differently from how it sounded.
- **Cost:** sentiment runs on the fast model (see "AI models"), about $0.002
  for a short call and roughly a cent for a 20-minute one.

## Status

In place: auth, tenancy, module gating, database, scorecard data and grading
maths, the UI for every page (Freehold design), the Settings page (theme,
profile, company name, module switches), a branded app icon and 404 page,
the call library and call detail (filters, stats, a player synced to the
transcript, delete), and call storage: uploads go to the private bucket and
calls are saved in Postgres. The whole pipeline works: transcription with
speaker labels, call type and outcome analysis, scorecard grading and
coaching, so calls end as `ready`.

Calls process in the background with progress shown, stalled calls are
detected, and failed calls can be retried. The AI runs on OpenAI
(`whisper-1`, `gpt-5.5`).

Quick search (⌘K) and the first-run checklist on the Overview are in place.

The Coaching page (`modules/coaching/ui/coaching-page.tsx`) groups ready
calls by employee: average share of scorecard points (scorecards differ in
size), trend of the newer half of calls vs the older half, grade counts, the
three most-missed steps, the latest focus and recent calls. The app layer
(`app/[tenant]/coaching/page.tsx`) builds a plain `CoachingCall` list from
the calls and scorecards modules, so the coaching module imports neither.

**Plays** (`coaching_plays`, owned by the coaching module): a concrete thing
for one team member to work on. When a member misses the same scorecard step
on at least two calls, their card suggests a play ("Work on 'Expectation
Statement'"), and anyone with `coaching.manage` assigns it in one click. The
assignee sees it under "Your plays" and marks it done. Managers see and
remove every play. The buttons are app-layer server actions passed into the
coaching module's page through slots.
