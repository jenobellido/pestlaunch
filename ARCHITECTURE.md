# Architecture

PestLaunch **Call Intelligence**: upload a call recording, get a transcript,
call type, outcome, scorecard grade and coaching. The UI and the backend API
live in this one Next.js app.

The code is feature-sliced. Each feature is a **module** that can be turned on
or off per tenant (pest control company).

```
proxy.ts                 Refreshes the Supabase session; sends signed-out users to /login
app/                     Routing only: thin pages, layouts, route handlers
  (auth)/                /login, /signup, /onboarding
  [tenant]/              UI, e.g. /noble-pest/calls
    _components/         TenantNav (enabled modules + user menu), PageSkeleton
    _lib/                requireModule (auth + membership + module check)
    calls/               Call library + upload
    calls/[callId]/      Call detail; composes panels from other modules
    scorecards/          The scoring standards
    coaching/            Employee coaching
  api/[tenant]/          Backend API, e.g. /api/noble-pest/calls
    _lib/                withModule (auth + membership + module check)
    calls/route.ts       GET list · POST create a call for an uploaded recording + process
    calls/uploads/       POST: a private storage path + one-time upload token
    calls/[callId]/      GET one call · DELETE call and recording (owner/manager)
core/                    Platform code every tenant gets. Not toggleable.
  calls/                 Shared call contract: CallType, TranscriptSegment,
                         CallAnalysisStep (how modules plug into processing)
  auth/                  Supabase Auth: server client, session, sign in/up/out actions
  config/                Validated server environment variables
  db/                    Drizzle schema and Postgres client
  modules/               Module manifest types, defineModule, dependency resolver
  tenancy/               Tenants, membership, access checks
  storage/               Private recordings bucket: signed uploads, download, playback URL, delete
                         (client.ts is the browser upload helper)
  ai/                    Groq client: Whisper transcription and structured-output chat
                         (generateObject: JSON schema + zod check, retries)
drizzle/                 SQL migrations generated by drizzle-kit
supabase/                Supabase CLI config for the local Docker stack
modules/                 Toggleable features
  registry.ts            Lists every module; resolves a tenant's enabled set
  registry.server.ts     Collects the analysis steps of enabled modules
  calls/                 Base module: pipeline, transcript, call type, outcome
  scorecards/            Grades calls with the manual scorecards (needs calls)
  coaching/              Per-call feedback and per-employee view (needs calls)
shared/                  Business-agnostic UI, helpers and config
  ui/                    Card, Badge, EmptyState, PageHeader, buttons, logo
```

Every module has the same shape:

```
modules/<name>/
  module.ts    Manifest: id, defaultEnabled, dependsOn, nav
  index.ts     Public UI API: manifest, components, types
  server.ts    Public server API: services, route handlers, analysis steps
  ui/          Components
  server/      Server-only code (starts with import "server-only")
  model/       Types and pure domain logic
  config/      Static data, e.g. the scorecards
  lib/         Module-private helpers
  server/schema.ts  The module's own database tables (optional)
```

## Dependency rules (enforced by ESLint)

`app → modules → core → shared`. A layer imports only from layers to its right.

- A module never imports another module. Share code through `core/` or
  `shared/`; compose modules in `app/` or the registries.
- `app/` imports a module only through `@/modules/<name>` or
  `@/modules/<name>/server`.
- Service functions take the tenant explicitly so every query is tenant-scoped.

## Data and auth

- **Postgres** on Supabase (production) or the Supabase CLI's Docker stack
  (local). Platform tables live in `core/db/schema.ts`; a module's own tables
  live in its `server/schema.ts` (e.g. `calls` in the calls module).
  drizzle-kit reads both and generates migrations into `drizzle/`.
- **Calls** are one row each in `calls`: status, file name, recording path,
  call type, employee, and JSON columns for the transcript, outcome and
  per-module `analyses`. Rows belong to a tenant and are always queried by it.
- **Auth** is Supabase Auth with email and password, using cookies through
  `@supabase/ssr`. `proxy.ts` refreshes the session on every request.
- **Tenancy:** `tenants`, `tenant_members` (role: owner, manager or rep) and
  `tenant_modules` (per-tenant module overrides). Sign-up creates the user, a
  tenant and an owner membership.
- **Authorization** is enforced in the app, not by RLS. Every table has RLS
  enabled with no policies, so Supabase's public REST API returns nothing.
  The server reads data over a direct Postgres connection and checks access
  with `requireTenantAccess` (pages) and `checkTenantAccess` (APIs). A tenant
  the user isn't a member of returns 404, the same as one that doesn't exist.
- **Recordings** go to the private `recordings` storage bucket, under a
  folder per tenant (`<tenantId>/<uuid>.<ext>`). It has no policies, so only
  the server (secret key) can read it. The API rejects a path outside the
  caller's tenant folder.
- Auth checks call `connection()` so they always run per request and never
  end up in a prerendered or prefetched shell.

## Call processing

Recordings never pass through our API, because they're often bigger than
the 4.5 MB request limit on serverless hosts:

1. `POST /api/[tenant]/calls/uploads` with `{ fileName, size }` checks the
   type and size (50 MB max) and returns a storage path in the tenant's
   folder plus a one-time upload token.
2. The browser uploads the file straight to storage with that token
   (`core/storage/client.ts`).
3. `POST /api/[tenant]/calls` with `{ path, fileName }` checks the file is
   there, creates the `calls` row (status `processing`) and runs
   `modules/calls/server/process-call.ts`.

The pipeline downloads the recording and saves each stage as it finishes, so
a failure keeps whatever already worked and sets status `failed` with the
error:

1. **Transcribe** (`transcribe.ts`) with speaker labels:
   - Groq Whisper (`whisper-large-v3`) returns timed segments. A vocabulary
     hint (pests, service plans) helps it spell the trade's words.
   - Segments Whisper marks as non-speech are dropped, and a recording with
     fewer than 5 words is rejected: on silence Whisper invents text such as
     "Thank you."
   - Whisper doesn't say who is talking, so `gpt-oss-120b` labels each
     segment employee, customer or unknown (phone menus, hold messages). It
     works in chunks of 40 lines, each shown the call's opening lines and the
     lines just before it. When one segment holds two speakers, the model can
     split it; the split is kept only if its pieces are exactly the segment's
     words, so no text is invented.
   - Consecutive lines from the same speaker are joined into turns of up to
     about 30 seconds.
2. **Analyze** (`analyze-call.ts`): one `gpt-oss-120b` request with a strict
   schema returns the call type, the employee's name, a short summary, the
   resolution (booked, retained, cancelled, resolved, follow-up needed,
   unresolved), key details and open follow-ups. The call type definitions
   come from the call manuals and judge the caller's real purpose, not the
   phone menu option. The prompt asks for facts said in the call only, with
   dates as spoken and no invented follow-ups.
3. **Module steps**: run the `CallAnalysisStep` of every enabled module
   (scorecards, coaching). Each result is stored under `analyses[moduleId]`.

The calls module never imports scorecards or coaching. The route asks
`registry.server.ts` for the enabled steps and passes them in. Turning a module
off for a tenant removes both its UI and its processing step.

## UI and design

The look follows the Freehold design system: dark by default, light when the
device is set to light (`shared/config/theme.ts` sets `<html data-theme>`
before first paint), the Outfit font, rounded cards and mint accent pills.

- Colour tokens are CSS variables in `app/globals.css`, exposed to Tailwind
  as `bg-card`, `text-muted`, `text-accent`, etc. Use tokens, not raw colours,
  so both themes work. Every fill has an `on-` partner for text on top of it.
- Shared building blocks are in `shared/ui/`. Each page uses `PageStack` and
  `PageHeader` so pages line up the same way.
- Module nav items carry an icon (`nav[].icon` in `module.ts`), shown in the
  sidebar and the mobile bottom bar.

## Call types and scorecards

From the call manuals in `../docs/call-manuals/`:

| Call type | Scorecard | Max | Gold | Green |
| --- | --- | --- | --- | --- |
| New customer (sales) | Sales Calls | 17 | 17 | 14+ |
| Retention | Retention Calls | 12 | 12 | 11 |
| Scheduling, billing, re-service | All Calls | 12 | 12 | 11 |
| Other | Not scored | | | |

Sections follow the manuals' four steps (Validate, Understand, Solve,
Verify), plus Pricing and Objections on sales calls. On sales calls with no
objections, the 4 objection points are awarded automatically.

The scorecards are data in `modules/scorecards/config/scorecards.ts`. Each
item carries its criteria, paraphrased from the manual's definition of that
step; the grader and the Scorecards page both show them, so managers and the
AI judge by the same rule.

Grading (`modules/scorecards/server/scoring-step.ts`): one structured-output
request gets pass/fail, an evidence quote and a one-line reason per item,
plus whether the customer raised objections. A quote is kept only if its
words really appear in the transcript, so every quote shown can be trusted.
Points and grade are computed in code from the scorecard, never by the
model.

## Module toggling

1. Each `module.ts` declares `defaultEnabled` and optional `dependsOn`.
2. A tenant stores overrides in `tenant.modules`, e.g. `{ coaching: false }`.
3. `resolveEnabledModules` applies the overrides, then turns off any module
   whose dependencies are off.
4. Every module page calls `requireModule(params, "<id>")`, and API routes use
   `withModule("<id>", handler)`. Server actions must check `isModuleEnabled`.
   Don't rely on a layout for this: Next renders layouts and pages in
   parallel, so a layout check alone still lets a disabled page render and
   send its data.
5. After changing a tenant's modules, call `revalidateTag(tenantCacheTag(slug))`.

## Adding a module

1. Create `modules/<name>/` with the shape above and register it in `registry.ts`.
2. If it analyzes calls, export a `CallAnalysisStep` from its `server.ts` and
   add it in `registry.server.ts`.
3. Add `app/[tenant]/<name>/page.tsx` (calls `requireModule` first) and a
   `loading.tsx` next to it (re-export `PageSkeleton`). Each page needs its
   own boundary so client navigations between modules stay instant.
4. For APIs, add `app/api/[tenant]/<name>/route.ts` using `withModule`.
